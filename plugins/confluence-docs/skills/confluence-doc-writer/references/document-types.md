# 문서별 구성 선택

사용자가 준 목차·양식이 우선이다. 아래는 선택 가능한 기본 구성이다. 불필요한 항목은 제거하고 자료에 없는 내용을 채워 넣지 않는다.

## 기술 설계서

목적과 배경 → 범위 → 요구사항 → 설계와 데이터 흐름 → 인터페이스/설정 → 대안과 선택 이유 → 검증 기준 → 미결 사항.

구현된 사실과 사용자·자료가 제시한 설계를 구분한다. 새로운 설계 제안을 요청받은 경우에만 별도 제안으로 작성하고 구현된 것으로 표현하지 않는다. API가 있으면 메서드·경로·요청/응답·오류를 자료에 근거해 정리한다. 저장소 분석 시 핵심 파일과 근거 위치를 연결하되 로컬 경로를 다른 독자도 접근 가능한 링크인 것처럼 표현하지 않는다.

## 운영 절차서

목적과 적용 대상 → 사전 조건 → 실행 단계 → 성공 확인 → 실패 시 대응/복구 → 참고 자료.

각 단계에 작업과 확인 가능한 결과를 붙인다. 명령은 실행 환경과 변수를 명시한다. 자료에 없는 복구 명령은 추측하지 않고 질문한다. 확인 예정 상태로 기재하는 것은 사용자가 그 표현을 확인한 경우에만 허용한다. 문서 작성 과정에서 운영 명령을 실행하지 않는다.

## 회의록

회의 제목과 제공된 일시·참석자 → 한 표 또는 안건별 상세 표. 양식 미지정 회의록은 [내용에 따른 선택 기준](templates.md)으로 직접 선택하고 양식 선택 질문을 하지 않는다.

기본 안건 표의 열은 안건 / 논의 요점 / 결정 사항 / 미결 사항이다. 여러 주제는 안건별 행으로 구분하며 한 주제로 합치지 않는다. 논의된 의견과 확정된 결정을 구분한다. 모든 안건 아래 별도 Action Item 목차를 두고 안건 / 작업 내용 / 담당 / 기한 표에 수행하기로 확인한 작업을 한 행씩 기록한다. 상태는 제공된 경우에만 선택 열로 포함한다. 한 안건에 여러 작업이 있으면 안건명을 반복해 모두 유지하고 논의 표에 중복하지 않는다. 안건의 경계나 결정·작업의 소속, 작업 수행 합의가 불분명하면 먼저 확인한다. 결정 문장이나 검토 의견만으로 작업을 만들지 않는다.

자료에 없는 결정·담당·기한은 질문하고 확정 또는 미정 상태를 확인한다. 미결 사항이 없으면 해당 열을 생략할 수 있다. 긴 셀은 목록이나 같은 안건의 세부 행으로 나누고 셀 병합·중첩 표는 피한다. 사용자·회사 양식의 지정 구조가 우선이며 기존 회의록 일부 수정에는 새 형식을 강제하지 않는다.

소수의 주요 안건을 각각 자세히 기록하는 양식은 [주요 안건 회의록](../assets/templates/meeting-focused.md)을 사용한다. 회의 정보 아래에 실제 안건별 제목을 두고, 각 제목 아래에 논의 요점 / 결정 사항 / 미결 사항의 세로 표를 반복한다. 후속 작업은 안건별 표에 넣지 않고 모든 안건 아래 별도 Action Item 표에 모은다. 안건 수를 맞추려고 내용을 만들거나 서로 다른 안건을 합치지 않는다. 미결 사항은 기재할 내용이 없으면 해당 행을 생략할 수 있다. 기존 한 표 방식과 선택 기준은 [템플릿 적용 규칙](templates.md)을 따른다.

## 모듈 업무 진행현황

모듈원들의 주기별 업무 확인에는 [모듈 업무 진행현황](../assets/templates/team-progress.md)을 사용한다. 상단 메타 정보 표와 요약을 만들지 않고 **과제 진행 현황**과 **Action Item**을 별도 표로 정리한다. 과제는 지속적으로 진행·결과·다음 단계를 follow-up하고, 일회성 업무는 개별 처리 내용과 결과를 확인한다. 두 종류가 같은 사람에게 함께 있을 수 있으며 분류가 애매하면 확인한다.

과제 표는 과제 / 담당 / 상태 / 진행현황·이슈 / 다음 확인사항·목표일, Action Item 표는 업무 / 담당 / 상태 / 처리 내용·결과 / 기한이다. 이슈·지원 요청은 해당 과제의 진행현황 셀에, 다음 확인 계획·대응과 제공된 담당·기한은 같은 행의 마지막 셀에 적어 함께 읽을 수 있게 한다. 별도 목차로 분리하지 않는다. 한 사람의 여러 업무를 모두 유지하고 같은 업무를 중복하지 않는다. 한 종류만 요청했거나 없다고 확인된 종류는 목차와 빈 표를 생략한다. 이전 보고서가 있으면 이번 변화를 대조하되 확인 없이 지난 상태를 현재 사실로 사용하지 않는다. 제공되지 않은 완료율·지연·일정은 만들지 않는다.

## 이슈·장애 보고

프로세스 종료·서버 중단·OutOfMemory 등의 상황 공유에는 [이슈 보고](../assets/templates/issue-report.md)를 사용한다. **발생 개요 → 영향 범위 → 대응 경과 → 원인 확인 및 근거 → Action Item**의 5개 목차로 작성한다. 처음 공유하거나 대응 중인 문서에도 사용하며 원인 확정·복구 완료를 작성 조건으로 요구하지 않는다.

발생 개요에는 대상·환경, 실제 관측 현상, 최초 확인 시각, 현재 상태와 확인 시점을 모은다. 영향은 확인한 업무·서비스·범위만 기록하고 아직 확인 중이면 명시된 상태를 유지한다. 타임라인은 실제 관측·조치·결과를 표로 정리하고 발생 시각과 확인 시각을 구분한다. 재시작이나 프로세스 기동만으로 정상 복구를 확정하지 않으며 실제 확인 방법과 범위를 적는다.

원인 미확인·확인 중이라는 답변은 그대로 기록한다. OOM 로그만으로 메모리 누수나 서버 전체 장애를 단정하지 않고 사용자·자료가 제시한 가설만 가설로 구분한다. 로그·지표·설정과 링크는 실제 확인한 자료만 사용한다. 후속 작업은 확인된 작업·담당·기한·완료 기준을 별도 Action Item 표에 담으며 조사나 재발 방지 작업을 임의로 추가하지 않는다. 명령이나 복구 절차가 문서에 있어도 문서 작성 요청만으로 실행하지 않는다.

## 일반 안내/변경 사항

독자가 알아야 할 변화 → 영향 대상 → 필요한 행동 → 적용 시점 → 참고 자료.

기술 구현보다 독자의 행동을 먼저 설명한다. 한두 문단으로 충분하면 목차나 관리용 메타데이터 표를 만들지 않는다.
