# 수치와 근거 일관성 검토

자료 수집 뒤 최종 작성 전에, 문서의 효과·원인·완료 범위 등 핵심 주장과 주요 수치를 확인한다. 문서를 생성하거나 일부 수정한 뒤에는 요약와 본문의 반복 표현도 다시 비교한다. 날짜·문서 번호 같은 모든 숫자에 계산을 강제하지 않는다.

## 사실과 미확인 내용

- 핵심 주장마다 사용자 답변 또는 실제 읽은 자료의 근거가 있어야 한다. 자료를 요약하면서 원문에 없는 이유·성과·범위·후속 계획을 붙이지 않는다. 문서에 없는 내용을 추측해 검토용 근거로 저장하지도 않는다.
- 완료한 작업과 확인된 효과는 별개다. 기능 추가만으로 장애 감소·비용 절감·안정성 확보를 쓰지 않는다. 수치가 함께 변했거나 조치 뒤에 복구됐다는 사실만으로 해당 조치가 원인임을 단정하지 않는다.
- 사용자나 자료가 제시한 정성 평가·기대 효과·목표·계획·원인 가설은 그 종류와 불확실성을 유지한다. 이 표시는 모델이 내용을 새로 추측해 넣는 예외가 아니다. 원인이 확인되지 않았다면 필요한 확인 질문을 하고, `원인 확인 중` 같은 표현은 사용자와 합의한 경우에만 쓴다.
- 자료를 읽을 수 없으면 확인하지 못한 것으로 관리한다. 링크·파일명만 보고 내용을 재구성하거나, 자료가 없다는 이유로 `문제 없음`·`효과 없음`·`계획 없음`으로 판단하지 않는다. 상충하는 자료 중 더 그럴듯한 쪽을 고르지 않는다.
- 새로운 업무 대안이나 원인 가설을 명시적으로 요청받으면 `제안`·`검토 가설`로 확인된 사실과 분리한다. 제안의 전제 중 확인되지 않은 회사 조건은 질문으로 남기며 구현·채택·검증된 것으로 쓰지 않는다. 문장 정리와 시각화 구성 제안에는 새로운 업무 사실을 만들 필요가 없다.
- 전달 전 요약·본문·표·그림의 문구와 연결 관계를 읽고, 근거 없는 추가 주장과 기대 효과의 실적 표현이 없는지 확인한다. 필수 사실이 빠졌거나 의미가 애매하면 해당 항목을 질문 필요로 돌린다. 생략 가능한 선택 항목은 템플릿 규칙에 따라 생략한다.

## 자료에서 검토 항목 만들기

- 사용자 답변과 접근 가능한 파일에서 관련 원문을 발췌해 sources로 연결한다. source id와 참고 위치를 유지한다. 실제 읽지 않은 자료의 문장을 만들거나 예시 데이터를 증거로 재사용하지 않는다.
- 수치는 원문의 값·단위·비교 기간·대상 범위를 확인한다. 실측(measured), 정성 평가(qualitative), 기대 효과(expected)를 구분한다. 단위나 전후 값이 없으면 먼저 질문한다. `약`, 범위, 표본 차이 등 불확실성을 제거해 확정 수치처럼 만들지 않는다.
- 변화율을 제시할 때는 감소율/증가율을 구분하고 계산 기준을 확인한다. 전후 단위가 다르면 자동 변환하지 않고 같은 기준으로 비교할 수 있는지 확인한다. 0·음수 기준은 변화율을 임의로 정하지 않는다. 단순히 전후 값만 제시하는 문서에 변화율 추가나 질문을 강제하지 않는다.
- 핵심 주장은 관련 원문 문장과 연결하고 그 문장이 해당 주장을 뒷받침하는지 읽는다. 인용 문장이 존재하는 것만으로 사실성·인과관계가 증명되는 것은 아니다.
- 완성 문서의 주요 수치를 모두 확인해 본문·요약·표의 반복 값과 종류·단위·기간을 occurrences로 연결한다. 도구에 넣지 않은 표현은 자동 검토되지 않으므로 실제 파일도 읽고 비교한다.
- 수치 없는 정성 효과는 claims로 검토한다. 전후 비교 수치를 새로 만들어 metrics에 넣지 않는다. 변경율을 제시하지 않는 단일 측정값은 원문과 직접 대조하며 전후 비교 도구를 강제하지 않는다.

## 로컬 읽기 전용 검사

Python이 있으면 [검토 도구](../scripts/review_facts.py)를 실행한다. 입력은 아래처럼 review JSON이며 진행 스냅샷의 review 객체를 직접 읽을 수도 있다. 검토 입력 파일은 로컬 `.confluence-docs/drafts/` 안에 둔다.

```text
python <스킬폴더>/scripts/review_facts.py <검토자료.json>
python <스킬폴더>/scripts/review_facts.py <진행스냅샷.json>
```

```json
{
  "sources": [{"id": "memo-1", "text": "9월 A 배치 평균 처리시간은 기존 20초에서 15초로 줄었다."}],
  "metrics": [{
    "id": "batch-time", "kind": "measured", "before": "20", "after": "15",
    "unit": "초", "period": "9월 동일 조건 비교", "scope": "A 배치",
    "direction": "decrease", "reported_percent": "20", "source_ids": ["memo-1"],
    "occurrences": [{"section": "Executive Summary", "field": "reported_percent", "value": "20"}]
  }],
  "claims": [{
    "id": "effect", "text": "A 배치 처리시간 감소", "kind": "measured",
    "metric_id": "batch-time", "source_ids": ["memo-1"],
    "evidence": [{"source_id": "memo-1", "quote": "기존 20초에서 15초로 줄었다."}]
  }]
}
```

위 자료는 일부러 20%를 적은 가상 예시다. 감소율 계산값은 25%이며 도구는 불일치를 반환한다. 값을 고치거나 사용자에게서 확인받은 상태로 바꾸지 않는다. 계산된 변화율은 직접 계산한 값으로 구분하고 사용자 제공 실측값이라고 부르지 않는다.

metrics는 전후 비교용이다. before/after는 숫자 또는 소수 문자열, direction은 decrease/increase다. before_unit/after_unit을 별도로 지정할 수 있다. occurrences의 field는 before/after/reported_percent이고, unit/period/kind가 다른 경우 함께 기록한다. 변화율 비교는 기재한 소수 자릿수의 반올림을 고려한다. 정밀도가 다른 근사값이나 다른 기준의 계산은 사람이 확인해야 한다.

claims에는 text, kind, source_ids와 evidence를 넣는다. evidence의 quote는 해당 source.text에서 실제 발췌한 문장이다. metric_id는 관련 전후 수치를 연결할 때만 넣는다. 검토 항목이 없거나 자료 이름만 있고 내용이 없으면 통과로 처리하지 않는다.

## 불일치 처리

불일치가 나오면 해당 항목을 질문 필요로 되돌리고 원문 값·기재한 표현·계산 기준을 짧게 제시해 사용자에게 확인한다. “20초→15초는 감소율 25%인데 메모의 20%는 다른 기준인가요?”처럼 묻는다. 자동으로 수치를 수정하거나 더 그럴듯한 자료를 고르지 않는다.

새 답변이 명확한 정정이면 해당 항목과 관련 요약를 갱신하고 다시 검토한다. 남은 불확실성은 사용자와 표현을 합의한 뒤에만 문서에 담는다. 해결되지 않은 항목을 조용히 빼서 최종 문서를 만들지 않는다. 자료 연결·계산 검사가 통과해도 원문이 주장을 뒷받침하는지 읽는 검토는 유지한다.

Python이 없으면 동일한 계산과 원문 대조를 수동으로 수행하고 자동 검사 실행을 주장하지 않는다. 이 검토는 웹 팩트체크나 외부 자료 전송을 포함하지 않는다.
