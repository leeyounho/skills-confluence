# 대화로 정보 채우기

## 메모에서 시작

처음 받은 설명은 정보 수집의 출발점이다. 짧거나 거친 메모라는 이유로 내용을 추측해서 완성 문서를 만들지 않는다. 선택한 템플릿의 각 항목에 제공된 사실을 대응시키고, 확정된 내용·애매한 표현·누락된 정보를 구분한다. 기존 대화와 첨부 자료에 있는 답은 다시 묻지 않는다.

문서의 의미를 바꾸는 해석, 완료 여부, 대상·범위, 원인, 효과, 수치의 기준·단위·기간, 담당·일정이 불명확하면 확인한다. 문장 다듬기와 HTML 태그 선택처럼 사실과 의미를 바꾸지 않는 편집은 자율적으로 한다.

`알아서 작성`·`보기 좋게 정리`는 사실을 추측하라는 요청으로 해석하지 않는다. 제공한 내용을 구성·요약하되 부족한 필수 사실은 계속 확인한다. 기대 효과나 원인 가설도 사용자가 설명하거나 자료에 명시한 경우에만 그 상태로 기록한다. 질문을 만들 때는 답을 암시하기보다 실제 확인한 내용과 근거를 묻는다.

## 질문과 답변

- 먼저 이해한 내용을 짧게 정리하고, 다음에 필요한 질문을 한 번에 1~3개씩 묻는다. 사용자가 자유롭게 설명할 수 있게 구체적으로 질문한다. 전체 양식의 빈칸을 한꺼번에 제출하게 하지 않는다.
- 질문은 문서의 목적·범위·핵심 결과부터 시작하고, 답변을 반영해 다음 질문을 고른다. 답변을 받을 때까지 미확정 내용을 사실로 쓰거나 최종 HTML을 생성하지 않는다.
- 해석 후보가 있으면 확인 질문으로 제시하되 기본 선택이나 답변 없음으로 확정하지 않는다. 이전 답변과 충돌하면 어느 내용이 맞는지 확인한다.
- 답변마다 확인된 내용과 남은 질문을 갱신한다. 주제가 잠시 바뀌어도 이미 받은 답을 유지하고, 새 정보와 관련된 항목만 다시 확인한다.
- 템플릿의 각 항목은 `확인 완료`, `질문 필요`, `표현 합의: 미정/확인 예정`, `표현 합의: 없음/해당 없음`, `자동 요약`, `선택 항목 생략`으로 구분한다. 항목별 근거와 남은 질문을 유지한다. 첫 질문 전, 상태가 바뀐 때, 사용자가 준비 상태를 물은 때에는 간단한 표로 보여준다. 매 답변마다 전체 설명을 반복하지 않는다.
- 공개 양식의 필수·선택·자동 요약 항목과 충분성 기준은 catalog.json을 따른다. 자동 요약은 별도로 질문하지 않고 확인된 본문에서 작성한다. 선택 항목이 자료에 없고 생략이 허용되면 질문을 늘리지 않는다. 선택 항목에도 충돌이나 애매한 사실이 이미 있다면 해결 전에 확정하거나 생략하지 않는다.
- 사용자가 모른다고 답하면 실제로 미정인지, 확인할 예정인지, 해당 없음인지 묻고 그 상태를 어떻게 문서에 담을지 확인한다. 이미 “일정은 미정으로 적어줘”처럼 상태와 표현을 지정했다면 합의된 답으로 취급하고 재승인을 묻지 않는다. 없는 정보와 해당 없음을 혼동하지 않는다. 같은 질문을 반복해 답변을 강요하지 않는다.
- 사용자가 중간 초안을 명시적으로 요청하면 대화에서 확인된 내용으로만 검토용 초안을 제공하고 미확정 항목을 분명히 표시한다. 추측으로 빈칸을 채우지 않으며 이를 최종 문서로 취급하지 않는다.

## 정보가 충분한 기준

다음 조건을 충족하면 추가적인 승인 질문 없이 템플릿에 맞춰 `.body.html`과 `.md`를 작성한다.

1. 사용할 양식과 문서 목적·대상이 자료 또는 대화에서 분명하다. 양식이 지정되어 있으면 그 양식을 따른다.
2. 각 필수 항목을 작성할 근거가 있고, 주장·수치·완료 상태를 바꾸는 애매함이나 충돌이 해결됐다.
3. 남은 미정·확인 예정·해당 없음 항목은 사용자가 그 상태와 문서 표현을 확인했다. 필수 정보가 미정이어도 그 상태를 명시해 작성하기로 확인한 경우에는 진행할 수 있다.
4. 선택 항목은 근거가 있거나 템플릿 규칙과 확인된 해당 여부에 따라 생략할 수 있다.

위 항목은 사실 정보의 준비 기준이다. [시각화 구성](diagrams.md)에 의미 있는 선택지가 남아 있으면 해당 구성 질문을 먼저 한다. 사용자가 이미 구성을 정했거나 판단을 맡긴 경우에는 최종 승인 질문을 추가하지 않는다.

질문에 답이 없거나 시간이 지났다는 이유로 정보가 충분하다고 판단하지 않는다. `확인 필요`라는 표시만 붙여서 정보 수집을 끝내지 않는다. 처음부터 위 조건을 충족한 상세 자료라면 불필요한 질문 없이 작성한다.

## 완료보고 질문 예시

첫 메모가 “처리 개선 작업 끝났고 속도가 좋아졌어”라면 먼저 완료 대상과 범위, 기존 문제, 실제 개선 결과를 확인한다. “속도”가 무엇을 뜻하는지, 측정된 효과인지 체감·기대 효과인지 묻는다. 이후 추진 작업과 산출물, 후속 계획을 채운다. 질문은 제공된 답에 따라 조절하고 아래 항목을 매번 모두 묻지 않는다.

| 항목 | 확인할 내용 |
| --- | --- |
| Executive Summary | 확정된 본문에서 완료 결과와 핵심 효과를 요약한다. 별도로 질문하지 않는다. |
| 배경 | 어떤 기존 문제나 요구 때문에 추진했는가? |
| 효과 | 확인된 실적인가 기대 효과인가? 수치가 있다면 비교 기준·기간·단위는 무엇인가? |
| 추진내용 | 실제 수행한 작업과 산출물은 무엇이며 미완료 작업이 남아 있는가? |
| 향후계획 | 후속 작업이 있는가? 있다면 제공 가능한 담당·일정은 무엇인가? |

## 이슈 보고 질문 예시

“프로세스가 내려갔고 OutOfMemory 로그가 있어” 같은 첫 메모에는 대상·환경, 최초 확인 시각, 현재 상태부터 필요한 1~3개를 묻는다. 이후 실제 영향과 조치·확인 결과, 원인 확인 상태, 후속 작업을 채운다. OOM이라는 오류명만으로 서버 전체 중단이나 메모리 누수를 질문의 전제로 삼지 않는다.

“원인은 아직 확인 중이고 영향 범위도 조사 중으로 적어줘”처럼 상태가 명시되면 해당 표현을 합의된 답으로 기록한다. 원인 확정을 기다리지 않으며 실제 대응 내용과 남은 작업이 충분하면 상황 공유 문서를 작성한다. 자료에 없는 상세 로그·지표·재발 방지안 때문에 질문을 늘리지 않는다. 복구됐다는 답변의 확인 방법이나 범위가 애매하면 필요한 부분만 확인한다.

## 선택적인 준비 상태 검사

대화 기록이 근거다. Python 도구는 기록한 상태의 누락·충돌만 검사하며 사용자 확인 여부나 내용의 사실성을 자동 판별하지 않는다. `confirmed`는 항목별 기준을 만족한 경우에만, `agreed_pending`/`agreed_none`은 사용자가 표현까지 확인한 경우에만 기록한다. 나머지는 `missing` 또는 `unresolved`다. 도구의 ready 결과를 근거 없이 최종 작성 권한으로 사용하지 않는다.

사용자가 파일 저장을 요청했거나 기존 작업 파일을 제공한 경우 상태 JSON을 사용할 수 있다. 여러 채팅에 걸쳐 이어쓰려면 [진행 저장·재개](progress.md)의 전체 상태 형식을 사용한다. 아래 sections-only 예시는 준비 상태 검사 전용이다. 기본은 대화 안에서 관리하며 새 채팅에 자동으로 유지된다고 보장하지 않는다. 회사 사실이 담긴 상태 파일은 공개 저장소나 배포물에 추가하지 않는다.

```json
{
  "sections": {
    "배경": {"status": "confirmed", "content": "확인된 추진 계기와 목표"},
    "효과": {"status": "unresolved", "content": "실측인지 기대 효과인지 확인 중"},
    "추진내용": {"status": "confirmed", "content": "확인된 작업·산출물·완료 범위"},
    "향후계획": {"status": "agreed_pending", "content": "사용자가 일정 미정으로 기재 요청"}
  }
}
```

```text
python <스킬폴더>/scripts/templates.py --select 완료보고 --state <상태파일.json>
```

로컬 양식에는 공개 기준을 자동 적용하지 않으므로 도구 대신 해당 양식을 읽고 준비 상태를 정리한다.
