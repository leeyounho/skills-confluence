# Claude/Codex 수동 동작 검토 사례

자동 테스트는 도구의 선택·준비 상태·HTML 규칙·내용 대조·미리보기 복사 처리를 검증한다. 아래는 실제 모델에 스킬을 제공해 확인할 대화 사례이며 자동 통과했다고 주장하지 않는다. 공개 가상 자료만 사용하고 페이지 게시·원격 전송은 하지 않는다.

## 거친 메모에서 완료보고

첫 요청: “완료보고로 작성해줘. 배치 개선 작업 끝났고 빨라졌어.”

기대 동작: 완료보고 양식을 선택하고 첫 질문을 1~3개로 제한한다. 완료 범위와 효과의 의미를 확인하며 최종 파일은 아직 생성하지 않는다. Executive Summary를 별도로 작성해달라고 질문하지 않는다.

후속 답변 자료:

- 목적·범위: 내부 A 시스템 야간 배치 개선. 기존 중복 조회로 대기가 길었음.
- 추진내용: 중복 조회 제거와 운영 반영 완료. 테스트 결과와 변경 내역 문서 있음. 미완료 작업 없음.
- 효과: 운영자가 대기 감소를 체감했지만 실측 수치는 없음. 정성 평가로 적어달라고 요청.
- 향후계획: 2주 운영 모니터링, 담당 김담당, 시작 일정은 미정으로 기재 요청.

기대 동작: 이미 제공한 답을 재질문하지 않는다. 숫자 개선율을 만들지 않는다. 일정 미정 표현을 재승인받지 않는다. 비교 표로 충분하면 그림 없이, 의미 있는 시각화 선택지가 있으면 구성 선택 후 Executive Summary → 배경 → 효과 → 추진내용 → 향후계획을 유지한 body HTML과 Markdown을 생성한다. 준비 상태는 자동 요약과 확인 완료를 구분한다. HTML 검사 결과와 실제 회사 편집기 검증을 구분한다.

## 목록·로컬 양식·기본 양식

요청: “사용 가능한 템플릿 보여줘.”

기대 동작: 목록만 안내하고 문서 정보 질문을 시작하지 않는다.

설정에 default_template=issue-report.md가 있을 때 “완료보고로 작성”을 요청한다. 기대 동작: 기본 이슈 보고로 바꾸지 않는다.

로컬 별칭 완료보고=사내완료.md를 지정하고 해당 파일을 준비한다. 기대 동작: 회사 양식의 실제 목차·작성 안내를 사용하고 공개 완료보고 기준을 강제하지 않는다. 파일을 없앤 뒤 같은 요청을 하면 공개 양식으로 조용히 대체하지 않는다.

예전 완료보고 저장본에 `summary` 항목이 있다. 기대 동작: 확인된 내용·근거·상태를 Executive Summary로 대응하고 현재 준비 상태를 다시 계산한다. 요약을 다시 질문하거나 회사 양식의 고정 제목을 바꾸지 않는다.

공개 목록에는 operations.md가 없고 issue-report.md가 있다. 예전 설정이 operations.md를 지정하고 로컬 파일도 없으면 양식이나 파일 위치를 확인하며 이슈 보고로 조용히 대체하지 않는다. 사용자가 별도로 보관한 운영 양식은 삭제하지 않는다.

## 대응 중인 이슈 보고

첫 메모: “운영 A 서버의 B 프로세스가 내려갔고 OutOfMemory 로그가 있어. 공유할 이슈 보고로 작성해줘.”

기대 동작: 이슈 보고 양식을 선택하고 최초 확인 시각·현재 상태·실제 영향 등 부족한 핵심 사실을 1~3개씩 질문한다. OOM 로그만으로 서버 전체 중단이나 메모리 누수를 단정하지 않고 최종 파일은 충분한 정보가 모인 뒤 생성한다.

후속 가상 자료: “10월 4일 09:10 KST에 프로세스 종료를 확인했어. 실제 발생 시각은 미확인으로 적어줘. 배치 A가 중단된 것은 확인했고 다른 영향은 조사 중이야. 09:15에 프로세스를 재기동했지만 업무 복구는 아직 확인 중이야. 09:20 기준 원인 미확인으로 적어줘. 김담당이 10시까지 배치 A의 실행 결과를 확인하기로 했고 완료 기준은 해당 배치의 정상 종료야. 다른 후속 작업은 없어.”

기대 동작: 발생 개요 / 영향 범위 / 대응 경과 / 원인 확인 및 근거 / Action Item의 5개 목차로 작성한다. 발생 시각을 확인 시각으로 대체하거나 종료 시각을 역산하지 않는다. 프로세스 기동과 업무 복구를 구분하고 원인 미확인·영향 조사 중 표현은 재승인 없이 유지한다. 원인 확정·힙 수치·재발 방지안이 없다는 이유로 작성을 막지 않는다. 김담당의 확인 작업만 기록하며 가상의 로그 메시지·지표·명령이나 추가 작업을 만들지 않는다. 표로 충분하면 다이어그램을 만들지 않는다.

변형: “서버는 정상이고 프로세스 로그에만 OOM이 있어”라고 정정한다. 기대 동작: 해당 현상과 관련된 영향·현재 상태를 확인해 수정하고 원인을 추측하지 않는다. 후속 작업이 없다는 답을 받으면 Action Item에는 없음으로 쓰고 빈 표를 만들지 않는다. 새 상태나 복구 결과가 이전 자료와 충돌하면 필요한 항목만 질문한다.

## 완료 문서 일부 정정

위 완료보고를 만든 뒤 “효과만 정정해줘. 체감 개선은 있었지만 원인을 분리할 수 없어서 효과는 아직 검증 중으로 적어줘.”를 요청한다.

기대 동작: 효과와 그 주장을 담은 Executive Summary만 수정한다. 배경·추진내용·향후계획을 이전 버전과 비교해 유지한다. 전체 질문을 다시 시작하거나 효과가 입증됐다고 표현하지 않는다. HTML·Markdown·기존 미리보기를 함께 갱신한다.

“배치 시간이 30에서 20으로 줄었어”처럼 단위·기간이 없는 새 답변은 먼저 질문하며 숫자를 최종 문서에 임의 해석하지 않는다.

## 최종 HTML과 코드 예제

문서에는 `{{변수}}`와 `<body>` 문법을 설명하는 코드 예제를 넣도록 요청한다. 기대 동작: HTML에서 코드 텍스트를 이스케이프하고 pre/code 안의 예시는 남긴다. 작성용 자리표시자와 실제 외곽 body 태그는 제거한다. 로컬 PNG는 입력 HTML에 깨진 상대 경로로 넣지 않고 그림 삽입 위치와 파일을 전달한다.

## 저장 후 새 채팅에서 재개

정보 수집 중 “여기까지 저장해줘”를 요청한다. 새 채팅에는 스킬과 저장 파일만 제공하고 “이어서 작성해줘”를 요청한다.

기대 동작: 선택 양식·확정 사실·합의된 일정 미정 표현과 남은 질문이 복원된다. 이미 확인한 배경과 추진내용을 다시 묻지 않는다. 저장 파일은 `.confluence-docs/drafts/` 안에 두고 공개 예시로 추가하지 않는다. 다시 저장해도 이전 파일을 유지한다. 현재 양식의 목차나 필수 기준이 바뀌면 해당 항목만 확인한다. 접근할 수 없는 원문이나 옛 컴퓨터 경로를 확인했다고 주장하지 않는다.

## 수치와 기대 효과 정정

자료: “9월 A 배치 평균 처리시간이 20초에서 15초로 감소했다. 메모에는 감소율 20%라고 적혔다.”

기대 동작: 감소율 계산값 25%와 기재값 20%의 기준을 질문한다. 자동으로 25%로 바꾸지 않는다. 새 답변으로 “25%가 맞고, 기간·범위는 동일 조건 9월 A 배치야”를 받으면 해당 수치와 관련 Executive Summary를 수정한다.

별도 자료: “운영 반영 전이고 처리시간 감소는 기대 효과야.” 문서 초안에는 “처리시간 감소가 입증되었다”가 있다. 기대 동작: 실측·기대 표현 충돌을 확인하고 확정 성과로 쓰지 않는다. 근거에 없는 인용문, 존재하지 않는 source id, Executive Summary와 본문의 다른 수치도 질문 필요로 표시한다. 검사 도구 통과만으로 원인의 인과관계가 증명됐다고 주장하지 않는다.

## 기본 비교 표와 구성 선택

양식·회사 설정 없이 “기존 중복 조회를 제거한 완료보고”를 요청하고 기존 방식과 반영된 변경을 제공한다. 기대 동작: 변경 비교는 As-Is / To-Be 열로 놓고, 수치 없는 변경에 측정값을 만들지 않는다. 기존 완료보고 목차에 표를 배치하며 같은 비교를 표와 그림으로 반복하지 않는다.

실제 대안 두 개와 각 안의 구성·제약을 제공한다. 기대 동작: 판단 기준을 행, 1안·2안을 열로 비교한다. 3안을 새로 만들지 않는다. 비용이나 우선순위가 없어 권고를 결정할 수 없으면 필요한 기준만 묻고 근거 없는 점수를 매기지 않는다.

전체 구조·정상 흐름·실패 분기가 있는 자료를 제공하고 그림 수량은 지정하지 않는다. 기대 동작: 의미 있게 다른 2~3개 구성을 먼저 제시하고 각 안의 그림 수·종류·위치·목적을 적는다. 사용자가 고르기 전에는 최종 그림·문서가 생성되지 않는다. 이후 “간결형으로, 핵심 흐름도 1개만”을 답하면 그 선택으로 진행하고 재승인을 묻지 않는다. 저장·재개에도 선택을 유지한다.

같은 자료에 “필요한 구성으로 알아서 작성” 또는 “표만”을 지정한다. 기대 동작: 구성 선택 질문을 반복하지 않는다. 부분 수정 요청에는 관계없는 기존 표·그림·문체를 바꾸지 않는다.

## 보고서 문체

자료: “사업명은 운영 고도화이고 중복 조회 제거를 완료했다. 운영자가 대기 감소를 체감했지만 실측 수치는 없다.”

기대 동작: 지정 사업명은 유지하고 본문은 실제 작업·정성 평가를 짧게 쓴다. `혁신적인 개선`, `시너지 창출`, `안정성 확보` 등 근거 없는 효과를 덧붙이지 않는다. 가상 문체 예시의 20초·15초를 사실로 재사용하지 않는다. 문장을 다듬어도 미정이나 기대 효과 상태를 유지한다.

## 완료 사실과 모르는 효과

자료: “알림 기능 추가와 운영 반영을 완료했어. 보기 좋게 알아서 완료보고로 작성해줘. 효과는 아직 모르겠어.”

기대 동작: 완료 사실을 유지하되 장애 감소·안정성 확보·비용 절감을 만들어 넣지 않는다. 효과를 어떻게 확인할 예정인지와 필요한 배경·계획을 질문한다. `기대 효과`라는 이름으로 모델의 추측을 넣지 않는다. 후속 답변으로 “효과는 아직 검증 전이라고 적고, 별도 계획은 없어”를 받으면 그 상태를 유지한다. `효과 없음`으로 바꾸거나 별도 승인 질문을 하지 않는다. Executive Summary와 As-Is / To-Be 표에도 같은 기준을 적용한다.

## 원인·가설·설계의 구분

자료: “서버 재시작 후 서비스가 복구됐어. 원인은 아직 확인 못했어.”

기대 동작: 재시작과 복구 사실을 원인으로 확장하지 않는다. 메모리 누수 같은 가설을 자동 추가하지 않고 원인 상태와 문서 표현을 확인한다. 이후 “가능한 원인 가설을 제안해줘”를 요청하면 검토 가설과 확인할 증거를 별도로 제시하며 실제 원인으로 확정하지 않는다.

기존 설계서를 정리할 때도 자료에 없는 API·재시도·저장소를 만들어 넣지 않는다. 사용자가 새 설계안을 요청하면 제안과 미확인 전제를 실제 구현과 구분한다. 접근할 수 없는 로그 링크만으로 로그 내용을 읽었다고 주장하지 않는다.

## 그림과 저장 자료에도 같은 사실 기준

자료: “A가 B에 전달하고 B가 C에 결과를 보내. 실패 시 동작은 모르겠어. 흐름도 1개로 정리해줘.”

기대 동작: 확인된 A → B → C 관계만 표현한다. 실패 분기·재시도·캐시·DB를 추측해 넣지 않는다. 실패 처리가 문서에 필수라면 질문하고, 선택 항목이면 근거 없는 분기를 생략한다. 그림 제목·화살표·캡션에도 확인되지 않은 성과·인과관계를 추가하지 않는다. 저장·재개 시 미확인 내용을 확정 사실로 바꾸거나 검토용 출처를 만들어 넣지 않는다.

## 여러 안건을 한 표로 정리한 회의록

가상 자료: “10월 1일 10시에 김담당·이담당이 참석했어. 안건 A는 작업 일정이고 금요일 반영을 결정했어. 김담당이 목요일까지 사전 점검, 이담당이 금요일까지 적용 결과를 확인해. A는 미결 사항 없어. 안건 B는 알림 방식이야. 화면 표시와 메일을 논의했지만 결론은 미정으로 적어줘. B는 김담당이 다음 주 월요일까지 비교 자료를 준비하고, 알림 대상 범위는 남은 쟁점이야. meeting.md 양식으로 정리해줘.”

기대 동작: 상단 일시·참석자와 안건별 기록 표를 만든다. A와 B를 다른 행에 두고 논의 요점·결정 사항·미결 사항을 같은 행에서 읽을 수 있게 한다. 아래 별도 Action Item 목차에 안건 / 작업 내용 / 담당 / 기한 표를 만들고 A의 두 작업과 B의 한 작업을 각각 한 행씩 기록한다. 각 안건·담당·기한 연결을 모두 보존하며 논의 표에는 작업 열을 남기지 않는다. B의 논의안을 확정 결정으로 쓰지 않는다. 제공한 기한 표현을 임의의 날짜로 변환하지 않는다. 확정된 A 결정이 있다고 B 결정 상태까지 확인 완료로 만들지 않는다. 같은 작업이나 논의·결정을 다른 목차에 반복하지 않는다. 표가 충분하므로 그림을 강제로 만들지 않는다.

안건명을 생략하고 “메일로 정했어”만 답한 변형에서는 어느 안건의 결정인지 질문한다. 후속 작업의 담당·기한이 빠진 변형에서는 필요한 값만 확인한다. 미결 사항 자료가 없으면 선택 열을 생략할 수 있지만 미확인 결정·작업을 `없음`으로 채우지 않는다. 긴 내용·여러 작업·세로줄 문자가 있는 경우 실제 항목을 빠뜨리지 않고 HTML 목록과 Markdown 이스케이프를 사용한다.

회사 양식이 별도 논의·결정·작업 섹션을 지정하면 그 구조를 유지한다. 기존 형식의 회의록에서 담당만 정정하는 요청에는 전체 표 형식으로 바꾸지 않는다. 이전 진행 저장본의 논의·결정·작업을 재개할 때는 항목 이름과 답변을 유지하면서 새 표의 안건 연결을 확인한다.

## 소수 주요 안건을 자세히 기록하는 회의록

위 A·B 가상 자료에 “주요 안건 회의록으로 작성해줘. 두 안건을 각각 자세히 정리하고 싶어”를 요청한다.

기대 동작: meeting-focused.md를 선택하고 상단 회의 정보 아래에 A·B 제목과 각각의 항목 / 내용 표를 만든다. 논의 요점·결정 사항·미결 사항을 세로 행으로 정리하고 작업 행은 넣지 않는다. 모든 안건 아래 별도 Action Item 목차와 통합 작업 표를 한 번만 만들며 A의 두 작업과 B의 한 작업을 각각 한 행씩 기록한다. 각 담당·기한과 안건 연결, B의 미정 결정과 남은 쟁점을 모두 유지한다. 전체 논의·결정 요약을 추가해 같은 내용을 반복하지 않는다. 안건을 세 개로 늘리지 않고 미결 사항이 없는 A는 해당 행을 생략할 수 있다. 확정된 상태를 다시 질문하지 않는다.

“안건별 상세 회의록”도 같은 양식을 선택한다. 한 안건만 제공하면 한 블록만 만들며 안건 간 연결이 애매하면 질문한다. “회의록으로, 두 안건을 한 표에 정리해줘”는 기존 meeting.md를 선택한다. 회사 지정 양식과 부분 수정 범위는 새 양식보다 우선한다. 진행 저장·재개 시 meeting-focused 선택과 각 안건의 답변·남은 질문을 유지한다.

## 내용에 따른 회의록 양식 자동 선택

가상 자료 1: 회의 일시·참석자를 제공하고, 두 안건 모두 한두 문장으로 논의·결정을 설명한다. 각각 작업 한 개의 담당·기한이 확인돼 있고 미결 사항은 없다. 요청은 “회의록으로 작성해줘”뿐이다.

기대 동작: 안건 수가 두 개라는 이유로 상세 양식을 강제하지 않고 meeting.md의 한 표를 선택한다. 이유를 한 문장으로 알리고 양식 선택이나 최종 승인을 묻지 않는다.

가상 자료 2: 같은 두 안건이지만 각 안건의 여러 대안·제약·반대 의견과 그 이유, 결정 근거, 여러 후속 작업과 담당·기한을 제공한다. 요청은 동일하게 “회의록으로 작성해줘”뿐이다.

기대 동작: 한 행에 넣으면 길어지는 내용을 보고 meeting-focused.md를 직접 선택한다. 실제 내용을 안건별 세로 표에 유지하며 선택 승인을 묻지 않는다. 첫 메모가 거칠고 필요한 사실이 빠졌다면 사실 질문을 먼저 하고, 양식 질문으로 사용자에게 판단을 돌리지 않는다. 결정·담당·기한은 추측하지 않는다.

같은 자료에 “한 표로” 또는 회사 양식을 지정하면 그 요청을 우선한다. 논의·결정은 짧지만 작업만 많아진 변형에서는 한 표 양식을 유지하고 후속 작업 표의 행을 늘린다. 여러 안건 중 두 주요 안건만 자세한 경우에도 나머지 실제 안건을 누락하지 않는다. 저장·재개와 부분 수정에는 이전 선택을 유지한다. 이름 조회 도구가 내용을 자동 분석했다고 주장하지 않는다.

## Action Item의 수행 합의와 상태

가상 자료: “김담당이 목요일까지 검토 자료를 만들기로 했고, 현재 작성 중이야. 알림 방식은 메일로 정했지만 개발 작업은 아직 정하지 않았어. 로그를 살펴보자는 의견도 있었는데 누가 언제 할지는 얘기하지 않았어.”

기대 동작: 검토 자료 작성은 별도 Action Item 표에 해당 안건·내용·김담당·목요일을 기록하고, 제공된 작성 중 상태만 선택 열로 덧붙인다. 메일 결정만으로 구현 작업을 만들지 않는다. 로그 확인이 실제 수행하기로 합의된 작업인지 확인하고, 합의됐다면 담당·기한을 묻는다. 상태가 없는 다른 작업에 미착수 같은 값을 덧붙이지 않는다. 두 공개 회의록 모두 같은 기준을 사용하며 작업을 논의 표나 다른 Action Item 항목에 중복하지 않는다. 회의 전체의 작업 없음이 확인되면 후속 작업 목차에 없음으로 적고 빈 표를 만들지 않는다.

## 모듈원들의 주기별 업무 진행현황

가상 요청: “모듈원 업무현황으로 작성해줘. 확인 주기는 3일이고 기준일은 10월 3일, 보고 기간은 10월 1~3일, 다음 확인은 10월 6일이야. 모듈은 A이고 김담당의 설계서 검토는 완료됐고 추가 작업은 없어. 이담당은 API 수정 업무를 맡았고, 목표일은 10월 6일이야. 지난 9월 30일 보고서도 첨부했어. 이슈·지원 요청은 없고 다음에는 API 수정 결과를 확인할 거야.”

기대 동작: team-progress.md를 선택하고 김담당의 완료 업무와 이담당의 업무를 모두 유지한다. 두 업무가 지속적으로 확인할 과제인지 개별 처리 후 종료되는 업무인지 자료에서 분명하지 않으면 확인한다. 이담당의 현재 상태와 이번 기간에 실제 한 일도 질문한다. 첨부한 이전 보고서를 읽고 당시 상태와 기준일을 보존하지만 지난 상태를 현재 사실로 자동 사용하지 않는다. 진행률·지연을 추정하거나 새 업무를 만들지 않는다.

후속 답변: “API 수정은 지속적으로 follow-up할 과제이고 진행 중이야. 입력 검증 변경을 마쳤고 응답 처리 수정이 남았어. 목표일은 그대로야. 설계서 검토는 일회성 업무로 끝났어.” 기대 동작: 이미 확인한 답을 다시 묻지 않고 상단 표·요약 없이 과제 진행 현황과 Action Item을 별도 표로 작성한다. 과제 표에는 API 수정의 담당·진행 결과·다음 확인사항·목표일을, Action Item 표에는 설계서 검토의 담당·완료 상태·실제 결과를 기록한다. 이미 완료한 일회성 업무의 기한을 새로 요구하지 않는다. 실제 이슈가 없고 다음 확인사항은 과제 표에 담겼으므로 불필요한 추가 목차를 생략한다. 이전 보고서는 덮어쓰지 않는다. 그림이나 완료율을 만들지 않는다.

“주간 업무보고” 별칭도 같은 양식을 선택하되 월~금 기간을 자동 가정하지 않는다. 이전 자료가 없는 경우에는 지난 실적·As-Is를 만들지 않는다. 모듈원이 상태를 아직 확인하지 못했다면 업무 대기나 지연으로 바꾸지 않는다. 회사 지정 양식과 기존 보고서 일부 수정 범위는 유지한다.

같은 담당자에게 과제와 일회성 업무가 모두 주어진 변형에서는 각 업무를 해당 표에 나눠 담고 어느 것도 누락하거나 중복하지 않는다. “과제만 확인해줘” 또는 “이번에는 일회성 업무만 있어”라고 범위를 정하면 다른 종류의 목차·빈 표를 만들지 않는다. 자료에 업무 종류가 빠졌다는 이유로 없는 업무라고 기록하지 않는다. 일회성 업무가 지속 과제로 바뀌었다는 답을 받으면 실제 내용을 보존해 이동한다.

이전 저장본의 보고 기준·요약·업무별 진행현황을 재개할 때에는 기존 사실과 합의된 표현을 유지하고 새 분류가 애매한 업무만 질문한다. 요약이나 상단 표를 다시 생성하지 않으며 준비 상태는 현재 두 업무 항목으로 다시 정리한다. 별도 이슈·지원 요청·다음 확인 계획에 있던 내용도 해당 과제나 업무의 행에 합치고 연결이 애매하면 질문한다. 미확인 내용을 옮기며 확인 완료로 바꾸지 않는다.

## 과제 진행과 이슈·지원 요청을 같은 행에서 확인

위 API 수정 과제의 추가 가상 자료: “응답 처리 수정은 진행 중인데 시험 환경 권한이 없어 테스트를 못 했어. 지원 담당은 박담당이고 10월 6일까지 권한을 열어달라고 요청했어. 반영일은 아직 미정으로 적어줘.”

기대 동작: 과제 진행 현황의 API 수정 행에서 입력 검증 완료·응답 처리 진행, 시험 환경 권한 이슈와 지원 요청을 함께 읽을 수 있게 한다. 다음 확인사항·목표일에는 권한 개통 확인과 테스트, 제공된 지원 담당·요청 기한을 담되 실제 반영일 미정 상태를 유지한다. 과제 담당과 지원 담당을 혼동하지 않는다. 이슈 및 지원 요청·다음 확인 계획의 별도 목차나 표를 추가하지 않고 없다는 이유로 이슈 없음 문구를 채우지 않는다.

같은 이슈가 여러 과제에 영향을 준다고 실제 연결을 제공한 경우에는 각 관련 행에 짧게 표시한다. 어느 과제에 속하는지 알 수 없는 요청은 먼저 확인한다. Action Item에 속한 문제는 해당 업무의 처리 내용 셀에 두고 과제 문제로 바꾸지 않는다. 예전 저장본에서 분리돼 있던 이슈·지원 담당·기한을 합칠 때 누락하지 않는다.

## 본문 소스 복사 미리보기

한글 문장·표·링크·여러 줄 코드를 포함한 문서를 작성하도록 요청한다. 기대 동작: body HTML·Markdown·복사 미리보기를 함께 제공한다. 브라우저의 본문 HTML 소스 복사 버튼으로 복사한 문자열이 body 파일 원문과 일치하며 제목·버튼·스타일·script를 포함하지 않는다. 자동 복사를 거부하는 환경에서는 소스 영역을 열어 선택하고 수동 복사 안내를 한다. 코드 안의 HTML 문법·엔티티·처음 줄바꿈도 보존한다.

본문 수치를 정정한 뒤 기대 동작: 미리보기를 재생성하고 복사 원문도 갱신한다. 미리보기 화면만 바꾼 채 이전 원문을 복사하지 않는다. 사용자가 미리보기를 제외하면 본문 파일의 소스 복사 방법을 안내한다. 회사 Confluence에 넣어보지 않은 결과를 검증 완료라고 말하지 않는다.

## 산출물 간 내용 대조

HTML 효과 표에는 15초, Markdown에는 20초인 산출물을 제공한다. 기대 동작: 위치·내용 차이를 찾아 원문 근거를 확인한다. 이미 사용자가 15초로 정정한 경우 오래된 Markdown만 동기화하고, 자료가 충돌하면 질문한다. 숫자를 자동 평균 내거나 단위를 추정하지 않는다. 표 셀 위치·결정 상태·링크 대상·코드 내용이 다른 경우도 확인한다.

상단 Markdown 제목과 body HTML의 제목 제외, 강조·일반 줄바꿈·그림 삽입 안내 차이는 문서 오류로 취급하지 않는다. 캡션과 그림 위치 대응은 별도로 확인한다. 병합 셀·참조 링크·각주가 있는 회사 양식에서는 지원 밖임을 알리고 실제 파일을 수동 대조하며 양식이나 내용을 삭제해 검사 통과를 만들지 않는다. 실행 도구가 없으면 자동 검사했다고 주장하지 않는다.

## 실제 원본을 사용한 수정 내역

기존 완료보고에서 “효과만 20%에서 15%로 정정하고 향후계획에 모니터링 작업을 추가해줘”를 요청한다. 기대 동작: 수정 전에 실제 원본을 고유 경로에 저장하고 효과·관련 Executive Summary·요청한 계획을 수정한다. 별도 changes Markdown에는 실제 변경 위치와 이전·이후 값·추가 작업을 표시한다. 관련 없는 본문을 고치지 않고 변경 이유나 효과를 추정하지 않는다. 검토 표를 Confluence 본문에 넣어 큰 목차를 늘리지 않는다.

원본 없이 “변경 내역도 정리해줘”를 요청하면 이전 내용을 재구성하거나 비교 완료라고 말하지 않는다. 새 문서에는 빈 변경 파일을 만들지 않는다. 그림 자체의 변경은 실제 이전·이후 파일을 확인하고 텍스트 대조만으로 이미지 내용 검증을 주장하지 않는다. 수정 전 저장본과 회사 자료는 공개 저장소·ZIP에 넣지 않는다.
